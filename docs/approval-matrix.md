# 审批功能的状态矩阵

这份文档的用途：**改动审批相关代码之前先看它，改完之后更新它。**

它存在的原因很具体 —— 0.7.2 到 0.7.5 连续四个版本修的都是同一个功能，
四次全部由用户实测发现。事后把状态空间画出来才看清：那四个 bug 是同一张表里的四个空格，
第一轮画表就能一次发现。被报告的路径是具体的、看得见的；**没被报告的路径在意识里根本不存在**，
所以必须写下来。

## 三个维度

**状态**（一个授权请求的生命周期）

```
pending ──手机提交──> responded ──结局到达──> resolved
   │                                            ▲
   └──────────── 电脑批准 / 超时 / 上游撤销 ──────┘
```

- `pending` — 已记账，等人点。**永不过期**（实测有等 607 分钟后正常批准的）
- `responded` — 已向 agent 提交，等结局。此状态不重放（否则用户会重复点）
- `resolved` — 有结局。`resolvedAt` 之后保留 10 分钟，为的是让迟到的点击能拿到准确说明

**结局来源**（同一个状态变化可以由不同方产生 —— 实测最容易漏的一维）

| 来源 | 桥怎么知道 |
|---|---|
| 手机批准 | 自己发的请求，直接知道 |
| 电脑批准 | 只能从会话文件的 `interaction_resolved` 读到 |
| 超时取消 | 同上，`outcome != 'selected'` |
| 上游撤销 | 同上 |

后三种桥都是**被动得知**，而唯一的信号源是文件。这就是 0.7.5 那个 bug 的土壤。

**进入路径**（用户/客户端怎么回到这个会话）

| 路径 | 技术含义 | 内存状态 |
|---|---|---|
| 页面加载 | 新 WebSocket + 全新 JS 上下文 | 前端归零，后端在 |
| 应用内导航 | 列表 ↔ 会话，同一个页面 | 两边都在 |
| 断线重连 | WebSocket 重建，页面没变 | 两边都在，但连接级记账丢了 |
| 桥重启 | 扩展重载 | **后端归零**，靠上游补发 |

## 覆盖矩阵

标注说明：`t12`/`t13` = 单元层；`e2e` = 半自动端到端；`手工` = 只能人测。

| 结局来源 ↓ 进入路径 → | 页面加载 | 应用内导航 | 断线重连 | 桥重启 |
|---|---|---|---|---|
| 手机批准 | t12 | t13 | e2e | e2e |
| 电脑批准 | t12 | t12 | e2e | e2e |
| 超时 / 取消 | t12 + t13 | e2e | e2e | e2e |
| 上游撤销 | t12（同取消） | e2e | e2e | e2e |
| 结局落在读取窗口外 | t12（降级行为） | — | — | — |

**观察者维度**（同一个状态，四个地方要一致）

| 观察者 | 数据来源 | 覆盖 |
|---|---|---|
| 手机浮窗 | `type:'permission'` + `session:open` 的 `pending` | t13 |
| 手机历史卡片 | 文件解析出的 `pending` / `resolved` | t13 |
| 会话列表徽标 | `liveState()` 按 pending/resolved 配对判定 | t9 |
| 电脑侧 | Kiro 自己的 UI | 手工 |

## 已知的降级行为（有意为之，不是 bug）

- **`resolvedOutcomes()` 只读尾部 1MB。** 结局落在窗口外时查不到，那条 pending 仍会被重放；
  用户点一次会失败一次，然后由「提交失败后核对」兜住并标记已解决。
  **代价是第一次点击必然失败。** 接受它，因为替代方案是全文件扫描。
- **桥重启后内存清空**，未回应的请求靠 Kiro 上游 `resendPendingPermissions()` 补发。
  它的触发条件是「此前未订阅」，而桥重启正好满足。这条路与本地重放互补，两条都要留。

- [ ] 四个观察者会不会出现不一致？
